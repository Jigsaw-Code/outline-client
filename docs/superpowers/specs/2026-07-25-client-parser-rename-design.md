# Client parse/build type rename design

## Problem

`client/go/outline/client.go` names three types whose names do not match their
roles:

| Type | Fields | Actual role | Name honest? |
|------|--------|-------------|--------------|
| `Client` | `sd`, `pr`, `reporter`, session | runtime object | yes |
| `ClientConfig` | `DataDir`, `Composer` | **parse environment / factory** — inputs to parsing, exposes `ParseConfig` + `New` | no |
| `ParsedClient` | `Transport`, `Info`, `reporterConfig` | **the parsed client config** — inert result of parsing | no |

Two things are wrong:

1. **A config is not a parser.** `ClientConfig.ParseConfig` is backwards: a
   config is the *result* of parsing, not the thing that parses. `ClientConfig`'s
   fields (`DataDir`, `Composer`) are *inputs to* parsing — it is a
   parser/factory wearing a config's name.
2. **The name is on the wrong object.** The type that actually holds a parsed
   client config is `ParsedClient`. So `ClientConfig` (not a config) and
   `ParsedClient` (the real config) are effectively swapped.

This is a **naming problem, not a structural one**. The two-phase parse→build
split is load-bearing and stays: `doParseTunnelConfig` in `parse.go` parses and
then reads only `parsed.Info` (FirstHop, ConnType) to answer the UI — it never
builds a `Client`. This split is design decisions D1/D2 in
`docs/superpowers/specs/2026-07-08-app-policy-separation-design.md`.

## Design

Pure rename. No behavior change — method bodies are identical; only receiver and
return type names change.

### Rename map (`client/go/outline/`)

| Before | After |
|--------|-------|
| `ClientConfig{DataDir, Composer}` | `ClientParser{DataDir, Composer}` |
| `(*ClientConfig).ParseConfig(keyID, text) (*ParsedClient, error)` | `(*ClientParser).Parse(keyID, text) (*ClientConfig, error)` |
| `(*ClientConfig).New(keyID, text) *NewClientResult` | `(*ClientParser).NewClient(keyID, text) *NewClientResult` |
| `ParsedClient{Transport, Info, reporterConfig}` | `ClientConfig{Transport, Info, reporterConfig}` |
| `(*ParsedClient).NewClient() (*Client, error)` | `(*ClientConfig).New() (*Client, error)` |

Resulting pipeline:

```go
ClientParser{DataDir, Composer}
    .Parse(keyID, text) (*ClientConfig, error)   // Go two-phase entry
    .NewClient(keyID, text) *NewClientResult      // gobind convenience: parse + build

ClientConfig{Transport, Info, reporterConfig}
    .New() (*Client, error)                       // build runtime resources
```

### Method-naming convention

The receiver decides whether the method names its object:

- `ClientConfig.New()` — the receiver **is** the client's config, so `New()`
  needs no `Client` suffix; the config builds the thing it configures.
- `ClientParser.NewClient()` — the receiver is **not** a client config, so it
  names the object it produces: `NewClient()`.

This removes the `New`/`NewClient` collision that a naive rename would create and
gives each method a name that earns its shape.

### Unchanged

- `Client`, `NewClientResult`, `NewClientComposer`, `NewReporterConfigParser`.
- Dependencies stay **struct fields** on `ClientParser` (`DataDir`, `Composer`) —
  matches the gobind zero-value construction native uses and the existing
  electron/vpn_linux call sites. Not promoted to `Parse()` arguments.
- The two-phase parse→build separation.

## Blast radius

### Go — edited directly

- `client.go` — the rename map above + doc comments (and the stale `Client`
  TODO comment left as-is unless trivially correct to touch).
- `parse.go:147` — `(&ClientConfig{...}).ParseConfig` → `(&ClientParser{...}).Parse`.
- `electron/main.go:126` — `outline.ClientConfig{}` → `outline.ClientParser{}`
  (`.New(...)` call becomes `.NewClient(...)`).
- `vpn_linux.go:62` — `ClientConfig{}` → `ClientParser{}` (`.New(...)` →
  `.NewClient(...)`).
- `client_test.go`, `parse_test.go` — `(&ClientConfig{}).ParseConfig/.New` →
  `(&ClientParser{}).Parse/.NewClient`. Field access `parsed.Info`,
  `parsed.reporterConfig` is unchanged.

### Native — source edited; gobind bindings regenerate at build

The mobile bindings (`Tun2socks` framework / `outline.aar`) are generated by the
cordova build from the Go package. The native source references the real gobind
names, so renaming the Go type ripples in:

- **Java** `client/src/cordova/android/OutlineAndroidLib/outline/src/main/java/org/outline/vpn/VpnTunnelService.java`
  - line 52: `import outline.ClientConfig` → `import outline.ClientParser`
  - line 236: `new ClientConfig()` → `new ClientParser()`
  - line 238: `.new_(id, transportConfig)` → `.newClient(id, transportConfig)`
    (Go `New` was escaped to `new_`; Go `NewClient` maps to `newClient`.)
  - `import outline.NewClientResult`, `outline.Client` unchanged.
- **Swift** `client/src/cordova/apple/OutlineLib/VpnExtension/Sources/PacketTunnelProvider.swift`
  - line 46: `OutlineClientConfig()` → `OutlineClientParser()`
  - line 57: `.new(id, providerClientConfigText:)` →
    `.newClient(id, providerClientConfigText:)`
  - `OutlineNewClientResult` unchanged.
- **ObjC** `PacketTunnelProvider.m` — no change; it calls through
  `SwiftBridge.newClient`.

This updates the "gobind-visible signatures preserved exactly" invariant from
the 2026-07-08 app-policy-separation spec (which listed `ClientConfig.New`); this
spec supersedes that line.

### Docs

- `client/go/outline/configregistry/README.md` **and** the byte-identical
  `configregistry/AGENTS.md` — update `ClientConfig.ParseConfig` →
  `ClientParser.Parse` and `ParsedClient.NewClient` → `ClientConfig.New`
  (lines 21, 32 in each). *(These two files being identical duplicates is a
  pre-existing smell, out of scope here.)*
- `docs/superpowers/specs/2026-07-08-app-policy-separation-design.md` — left as a
  point-in-time historical record; this spec supersedes its `ClientConfig.New`
  "preserved exactly" claim. No edit.

## Verification

- Go: `npm run action client/go/test` (or `go test ./client/go/outline/...`)
  plus `go vet ./client/go/outline/...`. All existing scenarios must stay green;
  no test assertions change beyond the type/method renames.
- Mobile bindings + native compile: `npm run action client/src/cordova/build android`
  (and/or `ios` / `macos`) regenerates the gobind bindings and compiles the
  native call sites, verifying the Java/Swift edits against the regenerated API.

## Non-goals

- No change to parse or build behavior, error codes, or wire formats.
- No collapsing of the parse and build phases.
- No de-duplication of the identical `configregistry` README/AGENTS files.
- No promotion of `DataDir`/`Composer` to method arguments.
